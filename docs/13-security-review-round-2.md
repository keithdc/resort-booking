# Security and guardrail review, round 2

Fresh, adversarial, read-only second pass over the API, the application guardrails (API and both Next apps) and the database
guardrails. Question asked: "what else are we missing?". Round 1 is `docs/10-security-review.md` (S-01 to S-27); this file does
not repeat what that file fixed. Findings here are numbered R2-01 onwards. Anything round 1 left open and still open is listed
as a carry-over, with fresh evidence.

Method: read every controller, guard, DTO, service and repository touched since round 1 (registration, invites, team, roles,
audit log, TOTP 2FA, Resend mail, DB roles, tenancy guard) plus migrations 001-029, `roles.ts`, the Next apps' middleware,
session route and CSP builder, the compose file, CI workflow, gitleaks config and env examples. Ran `npm audit` (full and
`--omit=dev`) and the API unit tests (`npx jest --testPathIgnorePatterns integration`: 116 suites, 2074 tests, all pass; the
integration suite was skipped on purpose because it connects to Postgres). No server was started, no database was touched,
nothing was exploited. "Confirmed" below means the code path was read end to end.

Labels: **Defect** (the code does not do what the docs or the obvious intent say), **Hardening** (works as designed, design is
weaker than it should be), **Owner decision** (needs a business call before code), **Carry-over** (round 1 item, still open).
Effort: S (under a day), M (days), L (weeks).

## 1. Summary

Counts: 0 critical, 4 high, 10 medium, 11 low, 3 info (28 findings).

Top findings, in order of risk:

1. **R2-01 (High, defect):** an `employee` can cancel any booking with reason `property_cancelled` (100 percent refund) or `goodwill` (any amount up to what was paid) and the money goes out through the provider. The docs and the isolation test say no money-out route is open to employees.
2. **R2-02 (High, latent defect):** public property and stay pages are resolved by slug alone, but slugs are only unique per organization. A second workspace can create the same slug and shadow or collide with another operator's public page.
3. **R2-03 (High, defect):** `GET /staff/calendar` and `/staff/reports` accept any date range. `from=0001-01-01&to=9999-12-31` builds millions of day objects in the single Node thread (any staff role, including employee).
4. **R2-04 (High, hardening of the guard design):** every production safeguard is `NODE_ENV === 'production'`. An unset or different value (`staging`, `prod`) leaves the mock payment "pay" endpoint open to anyone, registration open, and the fixed development 2FA key in use.
5. **R2-05 (Medium):** `resort_app` can UPDATE and DELETE `audit_log`, `payments` and `refunds`; the app never needs to.
6. **R2-06 (Medium, defect):** the org settings audit entry always lists all 12 field names (the DTO requires all of them), so an IBAN change is invisible in the log, and nobody is told.
7. **R2-07 (Medium, defect):** 2FA setup and enable need only a session, not the password; enabling does not end other sessions. A stolen session can lock the owner out or plant its own authenticator.
8. **R2-08 / R2-09 (Medium):** sessions are a fixed 7 days with no server-side idle limit, no last-used data, no device list; the admin cookie has no `Secure` flag and `/api/session` stores any string.
9. **R2-10 (Medium):** an admin receives the reset link of another account and can sign in as that person; the audit log then attributes the actions to the victim.
10. **R2-11 / R2-13 (Medium, defects):** `IP_HASH_SALT` is optional, so IP and email hashes are reversible; IPv6 clients rotate inside a /64 and defeat every per-IP limit.
11. **R2-12 (Medium, readiness):** refund retry can fire while the first provider call is still in flight and the provider call carries no idempotency key; a crash after commit leaves a refund `pending` forever with no reconciler.

## 3. Detailed findings

### R2-01 Employees can move money out through staff cancel (High, defect, confirmed)

`POST /staff/reservations/:id/cancel` is `@AllowRoles('admin', 'employee')` (`staff-bookings.controller.ts:52-55`). The body
carries `reason` (`guest_request`, `property_cancelled`, `goodwill`) and, for goodwill, `refundCents` (`staff-actions.dto.ts`).
`StaffBookingsService.cancelInput` has no role check: `property_cancelled` refunds everything paid
(`staff-bookings.service.ts:136-138`), `goodwill` refunds any integer from 0 to what was paid (`:139-147`). `BookingsService.cancelRow`
then records the refund and `RefundIssuer.settle` asks the provider to pay it out immediately. Docs claim the opposite:
`docs/10` ("Everything that moves money out ... is admin only") and the test title at `tenant-isolation.spec.ts:344`
("no route is open to employees that moves money out"). The test passes because it only inspects routes it classifies as
money-out (refund retry, mark-paid); cancel is classed as day-to-day (`:98`).

Exploit: a compromised or disgruntled employee account cancels every future confirmed booking as `property_cancelled`. Each
guest is refunded 100 percent, the stays are released, the revenue is gone. One audit row per booking, no alert, no cap.
`change-dates` has the same shape: `waiveFee: true` and `balanceSettledOutside: true` (employee reachable) let staff write off a
fee or declare a balance paid with nothing but a free-text note.

Fix (S): in `StaffBookingsService`, an employee may cancel only with `guest_request` (policy refund, as computed); `property_cancelled`,
`goodwill`, `waiveFee` and `balanceSettledOutside` need `admin`. Add the case to `tenant-isolation.spec.ts` by testing the service
with an employee. **Owner decision:** whether employees should have an amount cap instead (for example goodwill up to X, or any
refund over X needs an admin).

**Status: fixed (Phase A, hardening part 1).** Re-verified: the finding was right (the cancel route had no role check). What changed: `StaffBookingsService` now takes the signed-in `StaffAccount` and answers `403 FORBIDDEN_ROLE` for an `employee` who asks for reason `property_cancelled` or `goodwill`, for any explicit `refundCents` (even with `guest_request`), for `waiveFee` (in the change-dates quote and in the change itself) and for `balanceSettledOutside`. Refund retry and mark-paid were already `@RequireRole('admin')` on the route (re-verified, no other staff route moves money: rate, discount, extra, property and organization routes are all admin only). **Decision recorded:** employees keep cancelling and moving dates under the guest policy only (policy refund as computed, normal rebook fee, a cheaper stay refunds the difference per the policy); everything that is a refund decision, a write-off or a manual payment declaration is admin only. This matches `docs/07-cancellation-policy.md`: the policy decides, staff overrides are an admin call. The amount-cap alternative is still available as an owner decision (section 6, item 1) and would be a small change in `requireAdminForCancel`. UI: `StaffCancelDialog` shows only the "Guest asked" choice (plus a note) to employees, `StaffChangeDatesDialog` hides "Waive the change fee" and the outside-payment checkbox (shows "an admin has to confirm"), `RefundDetailDialog` hides Retry and "Mark as refunded" (new `useIsAdmin` hook in `shared/hooks/use-staff-role.ts`, not-admin while loading). **Owner addition (same day):** an employee also gets `403 SAME_DAY_ADMIN_ONLY` for cancel, change-dates quote and change-dates when the booking's check-in is today or past in the PROPERTY's timezone (`isCheckInTodayOrPast` in `bookings.rules.ts`, which reuses `wholeDaysBetween`, the same day count as the refund ladder, with `BookingReader.todayFor`; the ladder and snapshot are unchanged). The cancel preview returns `canCancel: false` plus the message to an employee. Admins and guests are unaffected. Admin UI: stay detail disables Cancel and Change dates with the message, the change-dates dialog takes a `lockedReason`, and the cancel dialog still shows the exact policy refund for allowed bookings. Boundaries tested: check-in tomorrow allowed, today and past refused, a non-UTC property (Auckland vs Paris at 21:30 UTC), a daylight saving date, admin allowed. See also `docs/07-cancellation-policy.md`, "Staff cancellations". Tests: `staff-bookings.service.spec.ts` (employee matrix and admin still allowed), `tenant-isolation.spec.ts` (renamed and rewritten: `EMPLOYEE_MONEY_ROUTES_GATED_IN_SERVICE` must list exactly the employee-reachable money-touching writes, the pure money-out routes must be `['admin']`, and no employee route may match the forbidden path list), admin `staff-cancel-dialog`, `staff-change-dates-dialog`, `refund-detail-dialog`, `refunds-page` and `use-staff-role` tests.

**Status update (owner decisions, supersedes the employee rules above where they differ): money access is a per-person permission.** (A) Instead of "admin only", an admin can give an employee **"Can handle refunds and money actions"** (`staff_users.can_manage_refunds` and `staff_invites.can_manage_refunds`, migration 031, default false; `StaffAccount.canManageRefunds` is true for every admin and for an employee only with the flag, read from the database on every request in `findStaffBySessionTokenHash`, so a grant or removal applies from the next request with no session cache). With money access a person may: retry a failed refund and mark a hand refund as paid (route-level `@RequireMoneyAccess()` in `RoleGuard`, replacing `@RequireRole('admin')`), choose any amount and the reasons `property_cancelled` / `goodwill`, waive the rebook fee, mark `balanceSettledOutside`, and cancel or change a booking on its check-in day (`hasMoneyAccess` in `StaffBookingsService`). Without it nothing changes from the previous paragraph (policy only, `403 FORBIDDEN_ROLE`). **Audit:** every one of those routes is `@Audited` with a `details` builder (`staff-audit-details.ts`): actor id (the row), name, role and `viaRefundAccess` in the metadata, the booking reference, the refund amount / percent / reason / status, `waiveFee` and `balanceSettledOutside`; never a note, email, bank detail or token. Before this change retry, mark-paid, cancel and change-dates were audited by action and target id only (no role, amount or reference), so the metadata is new; no action was missing. Granting or removing the permission is admin only (`PATCH /staff/team/:staffId` with `canManageRefunds`, tenant-scoped through `staffUser`), writes `team.refund_access_granted` / `team.refund_access_removed` (who changed whose access, the member's name and the new value), is refused for an admin target (`REFUND_ACCESS_NOT_FOR_ADMIN`) and for yourself (`CANNOT_CHANGE_OWN_REFUND_ACCESS`, so nobody can grant themselves money access), and becoming an admin clears the stored flag so a later demotion never restores an old grant. The permission can also be set at invite time (employee invites only, copied to the account on accept, never stored for an admin invite). `tenant-isolation.spec.ts` now keeps two reviewed tables (service-gated money routes, route-gated `MONEY_ACCESS_ROUTES`), runs the real `RoleGuard` on the latter for an admin, an employee with and an employee without the permission, and still enumerates every route. (B) **Same-day rule corrected:** an employee WITHOUT money access can cancel a booking whose check-in is today or past (property timezone), but the refund is forced to zero (percent 0, amount 0, refund text "Staff cancelled on the check-in day without refund access: no refund"); the preview shows `canCancel: true`, refund 0 and the note; this replaces `403 SAME_DAY_ADMIN_ONLY` for cancel. Change-dates (and its quote) on such a booking stays `403 SAME_DAY_ADMIN_ONLY` for them (a money difference). Admins and permission holders get the ladder and custom amounts. `isCheckInTodayOrPast` and its boundary tests are unchanged. Admin UI: `useCanManageRefunds` (admin, or employee with the flag) drives the Refunds page, cancel and change-dates dialogs and the stay detail; Team shows "Full access" / "Refund access" / "Policy refunds only", an invite checkbox and a grant/remove action with a confirm. The "amount cap" alternative of the owner decision below is not built: the permission is all-or-nothing. See `docs/07-cancellation-policy.md` ("Staff cancellations") and `docs/04-product-domain.md` ("Staff accounts and roles"). New properties' defaults (one 0-day 0% refund row, two on-request guest extras) are in `docs/07` and `docs/04`, not a security item.

### R2-02 Public slug lookup is global, uniqueness is per organization (High, latent defect, confirmed)

`properties` has `UNIQUE (organization_id, slug)` (`001_init.sql:29`) and `houses` `UNIQUE (property_id, slug)` (`:46`), and the
staff check `slugTaken` is per organization (`property.repository.ts:304-315`). The guest routes resolve by slug only:
`WHERE p.slug = $1` (`:127`), `WHERE p.slug = $1 AND h.slug = $2` (`:199`), house lists and availability
(`:167`). Two workspaces can both own `beach-house`.

Scenario (needs registration open or a second organization, both supported by round 1's work): workspace B creates a published
property with the slug of workspace A's published property. `GET /properties/beach-house` and its houses, quotes and
availability return whichever row Postgres returns first (no `ORDER BY`); the guest site may show B's content, or A's guests may
be shown B's stays. A hostile tenant can deliberately squat the slug of a competitor or of a known brand. Holds use house ids,
so a guest on a confusing page books the wrong operator.

Fix (M): one globally unique public slug (unique index on `lower(slug)` for published properties, or on all) or resolve the
public site by organization (host name or `organization` path segment). Also make `GET /identity/organization` (first organization,
`identity.repository.ts:getSettings(null)`) follow the same decision. **Owner decision:** one operator forever, or several (round 1
decision 3).

**Status: fixed (Phase A, hardening part 1) as a global uniqueness rule.** Re-verified: right. What changed: migration `030_global_property_slug.sql` adds `UNIQUE INDEX properties_slug_lower_key ON properties (lower(slug))`, after settling any existing duplicates deterministically (the oldest property keeps the slug, later ones get their short id appended, each with a NOTICE; nothing is deleted; replayable; no new grants because there is no new table). Checked on a throwaway database (all migrations 001 to 029, a second organization with a duplicate slug in other case, then 030 twice): the later property was renamed `pine-coast-b1cd59de`, the replay was a no-op and a new duplicate was refused with 23505. `PropertyRepository.slugTaken(slug, exceptPropertyId)` now looks across every organization, ignoring case. `PropertyService`: a typed slug that is taken answers `409 SLUG_TAKEN` ("That web address is already used by another property. Please choose a different one.") on create and update, a database unique violation from a race maps to the same 409, and a slug derived from the name still gets a suffix (so a plain name keeps working). Houses are looked up by (property slug, house slug) and are unique inside the property, so they are covered. Not changed: `GET /identity/organization` still returns the first organization (owner decision: one operator or several, section 6 item 2). Tests: `property-slug.spec.ts`, `organization-scope.spec.ts`, `migrations/global-property-slug.spec.ts`. The owner applies the migration by restarting the API.

### R2-03 Unbounded date range on staff calendar and reports (High, defect, confirmed by reading; not run)

`StaffRangeQueryDto` validates only the shape of `from` and `to`. `assertRange` only requires `to` after `from`
(`reservations.service.ts:388-395`). `getCalendar` then runs `eachIsoDate(from, to).map(...)` (`:85`) and `getReport` calls
`eachIsoDate` again and loops over it (`:136`). `eachIsoDate` pushes one string per night (`reservations.rules.ts:86-97`). A range of
`0001-01-01` to `9999-12-31` is about 3.65 million nights, then an object per night, per request, on the single event loop; a few
parallel requests exhaust memory. Both routes are open to `employee`. (The guest availability endpoints do cap the window at 24 months,
`availability.rules.ts:11`; the staff ones forgot.)

Fix (S): in `assertRange` refuse more than 731 nights (calendar) and 1096 (reports); add the cap to the `previousRange` too. Add a test with the extreme dates.

**Status: fixed (Phase A, hardening part 1).** Re-verified: right, with one correction: the exact pair `0001-01-01` to `9999-12-31` was already refused (`Date.UTC` maps year 1 to 1901, so `parseUtcDate` returned null), but `0100-01-01` to `9999-12-31`, or `2000-01-01` to `2100-12-31`, was not. What changed: `staffRangeProblem` in `reservations.rules.ts` (used by `assertRange` for `GET /staff/calendar` and `/staff/reports`, and so for the report's previous-period window, which has the same length): both dates must be real, `to` (exclusive) after `from`, inside 2000-01-01 to 2100-12-31 (`400 INVALID_DATES`), and at most 400 nights (`400 RANGE_TOO_LONG`, message "Choose at most 400 days at a time"). 400 matches the admin app's own `MAX_CUSTOM_RANGE_DAYS`. Other range inputs checked: guest availability is already capped at 24 months, the audit log `from`/`to` only filter a paged query (limit 100), rate periods are stored as a start and end and never expanded per day. Admin: calendar asks for one month; every report preset is at most 366 nights, now pinned by a test over four years and every day of the year. Tests: `reservations.rules.spec.ts`, `reservations.service.spec.ts` (extreme dates, 400 and 401 nights, no query runs), admin `report-range.test.ts`.

### R2-04 Production guards depend on `NODE_ENV` being exactly `production` (High, hardening, confirmed)

**Status: fixed (hardening Phase A).** `environment.ts`: only `NODE_ENV=development` or `test` is a development run (`isDevelopmentMode`); `isProduction()` now means "production-like" and is true for unset, `staging`, `prod`, `Production` and typos. Startup validation then fails fast: an unset or unknown `NODE_ENV` is itself an error with a clear message, and every production check (CORS, TLS, database roles, `TWO_FACTOR_ENCRYPTION_KEY`, mail, `IP_HASH_SALT`) is an error instead of a warning. The mock payment provider needs `NODE_ENV` development/test AND `ALLOW_MOCK_PAYMENTS=true` (`payment-provider.factory.ts`); the start is refused when the mock is configured without the flag, when the mock is configured on a production-like run, and when `ALLOW_MOCK_PAYMENTS=true` is set on a production-like run, so `POST /payments/:id/mock/complete` cannot exist on a server. Registration (closed unless `ALLOW_REGISTRATION=true`), the 2FA key fallback, automatic migrations and the dev-password allowance all follow the same rule. `npm run start:dev` sets `NODE_ENV=development`, `npm test -w api` sets `NODE_ENV=test`; `apps/api/.env.example`, README, docs/05 and docs/11 updated. Both Next apps: CSP relaxation only for `NODE_ENV === 'development'` and HSTS for everything else (Next sets `NODE_ENV` itself for `dev`/`start`/`build`). Tests: `environment.spec.ts`, `payment-provider.factory.spec.ts`, `two-factor.cipher.spec.ts`, `team.service.spec.ts`, `database-settings.spec.ts`. Not done: a rate limit on the mock route (it no longer exists outside development; see R2-14).

`isProduction(env)` is `env.NODE_ENV === 'production'` (`environment.ts:23-25`). Round 1's S-26 added a startup check, but it
warns (not stops) when `NODE_ENV` is unset (`environment.ts` last warning) and treats anything other than `production` as "not
production". Consequences when a deploy has no `NODE_ENV` (the `start` script sets none, `apps/api/package.json`), or uses
`staging`, `prod` or `Production`:

- `createPaymentProvider` allows the mock (`payment-provider.factory.ts:25`) and `PAYMENT_PROVIDER` defaults to `mock`. `POST /payments/:paymentId/mock/complete` has no auth and no rate limit (`payments.controller.ts:27`, `payments.service.ts:162`): anyone holding a card hold can confirm a stay without paying. The payment id is returned by `POST /holds/:holdId/payment`, which is also public.
- Registration is open (`team.service.ts:60`): anyone creates a workspace and an admin (R2-02, R2-10).
- `TWO_FACTOR_ENCRYPTION_KEY` falls back to the fixed key whose seed is in the repo (`DEV_KEY_SEED` and the constructor fallback in `two-factor.cipher.ts`), so enrolled secrets can be decrypted by anyone with a database dump.
- Localhost CORS, the database-role and TLS checks, and the Redis/CORS errors become warnings.

Fix (S): invert the default. Refuse to start unless `NODE_ENV` is one of `development`, `test`, `production`; treat everything that is
not `development` or `test` as strict. Require an explicit `ALLOW_MOCK_PAYMENTS=true` (refused when strict) for the mock. Make
`mock/complete` return 404 unless that flag is on.

### R2-05 The app role can rewrite the audit log and financial history (Medium, hardening, confirmed)

**Status: fixed (Phase B, payments hardening).** Re-verified first: true (`roles.ts` granted `SELECT, INSERT, UPDATE, DELETE` on every table and by default privilege; the code never updates or deletes `audit_log`, never deletes `payments`, `refunds` or `booking_changes`). Fixed in two layers. Privileges (`restrictedTableStatements` in `roles.ts`, applied by `db:setup-roles` AND after every migration run by `applyPendingMigrations`, so a table the owner creates later cannot keep the blanket grant): `resort_app` has `SELECT, INSERT` only on `audit_log` and `booking_changes`; on `payments` and `refunds` `SELECT, INSERT` plus `UPDATE` of the settlement columns only (payments: `status, failure_reason, inventory_block_id, updated_at`; refunds: `status, provider, provider_ref, failure_reason, resolution_note, resolved_by_staff_id, resolved_at, updated_at, processing_started_at, attempts, key_generation`); no `DELETE` on any of them. Triggers (migration 032, defence in depth for ANY role, the owner included): `audit_log` and `booking_changes` raise on UPDATE, DELETE and TRUNCATE (the only exception: the `staff_user_id ON DELETE SET NULL` of an erased staff account); `payments` and `refunds` raise on DELETE and TRUNCATE, freeze amount, currency, provider, links, kind and reason after creation, and enforce the status machine (payment `requires_payment -> succeeded | failed | cancelled`, `failed | cancelled -> succeeded` for a late success, a succeeded payment never changes; refund `pending -> succeeded | failed`, `failed -> pending (retry) | succeeded`, a succeeded refund never changes). `payments.inventory_block_id` may move only on a succeeded payment (date changes move the money). Escape hatch for a retention or erasure job: the owner runs `SET LOCAL resort.record_maintenance = 'on'` inside one transaction (transaction-local, so it cannot be left on). `db:verify-roles` gained 17 probes (append to audit log allowed, rewrite/delete refused, amount/currency refused, delete refused, webhook table rules); the integration test proves the triggers as owner and the grants as `resort_app` on a throwaway database, and the replay of 032 to 034. Not done: writing the audit row in the same transaction as the money change (the audit write is still fire and forget; see docs/14, "what to alert on"). Files: `migrations/032_financial_record_guards.sql`, `shared/database/{roles,role-probes,migration-files}.ts`, `docs/11-database-access.md`.

`buildRoleStatements` grants `SELECT, INSERT, UPDATE, DELETE` on all tables to `resort_app` and the same by default privilege for every
future table (`roles.ts:202,213-214`). That includes `audit_log`, `payments`, `refunds`, `booking_changes`, `discount_redemptions` and
`inventory_blocks`. A SQL injection or a bug (or a compromised API process) can rewrite who did what, delete refunds, or edit a
payment. The application code never issues UPDATE or DELETE against `audit_log` and never deletes `payments`, `refunds` or
reservations (only `discount_redemptions`, rates, discounts, extras, sessions, challenges and similar; grep of `DELETE FROM`).
Also, `audit_log.staff_user_id` is `ON DELETE SET NULL` and the audit write is fire and forget

### R2-18 Login capacity and lock-out as denial of service (Low, hardening / owner decision, confirmed)

### R2-19 Recovery codes use plain SHA-256; the 2FA key cannot rotate (Low, hardening, confirmed)

## 7. Addendum: bookings made by staff, and money recorded by hand (migration 040)

New staff routes: `POST /staff/reservations/quote`, `POST /staff/reservations` (creates a confirmed pay-at-hotel booking) and `POST /staff/reservations/:id/mark-paid`. Checked against the same rules as the rest:

- **Tenancy:** `@TenantScoped` on the house (body) and the booking (param): another organization's id answers 404 before the handler runs; the creator also re-checks the house's organization. All three routes are in the reviewed role matrix (`BOTH`) and the two writes are audited.
- **A guest can never pick pay at hotel:** `CreateHoldDto` still accepts only `card` and `bank_transfer`; a test fails if that changes. The staff DTO accepts only `pay_at_hotel`, trims and bounds every string, validates email and phone, and refuses unknown fields, so `paymentStatus`, `paidCents`, `totalCents` and `organizationId` cannot be set from the request.
- **Money fields are server-set:** price comes from the same quote code a guest gets (rates, then automatic discounts), saved as a snapshot with the day's cancellation policy; `paid_cents` is 0 and `payment_status` is `pending` on insert, and only the conditional `UPDATE` in `markPaid` can change them.
- **Database:** CHECKs keep a pending booking unpaid and pay-at-hotel only; a trigger refuses `paid -> pending` (even for the owner role) and a tick without `paid_at`. The no-overlap constraint still decides double bookings (409, nothing saved). Tested against a real Postgres in `migrations/staff-bookings.integration.spec.ts`.
- **Privacy in the audit log:** `booking.created_by_staff` and `booking.marked_paid` record who, role, reference, stay id, dates, party size, amount and method; never the guest's name, email, phone or note (tested).
- **Open question:** employees can tick a booking paid. It makes the booking's `paid_cents` equal its total, which later feeds the policy refund (and refunds themselves still need money access). If cash handling should be admin-only, change the role on the route. A dual-control rule (a second person confirms) is not built.
- **Not covered:** per-user rate limit on creating bookings (staff are authenticated and audited; a runaway client could still fill a calendar), and an alert for pending bookings whose check-in has passed (SQL in docs/14).
